## 1. Zabbix 系统概述


### 1.1 什么是 Zabbix

Zabbix 是一款开源的企业级 分布式监控与告警平台，用于对网络设备、服务器、虚拟机、容器、应用程序及数据库等 IT 资源进行统一的可用性监测与性能指标采集。它支持从数台到数十万台主机的规模化监控，并提供数据采集、阈值判定、故障告警、可视化展示与容量分析等完整能力。

Zabbix 采用 C/S 与 B/S 混合架构：由 Zabbix Server 等后台组件负责数据采集与处理，由 Web 前端提供图形化管理界面，底层使用关系型数据库持久化配置与历史数据。


### 1.2 核心能力

数据采集：支持 Agent 主动/被动采集、SNMP、IPMI、JMX、SSH/Telnet、HTTP 检查、脚本自定义等多种采集方式，覆盖主机与网络设备的各类指标。

阈值告警：通过触发器（Trigger）定义逻辑表达式，条件满足时生成告警事件，并经由邮件、短信、Webhook 等渠道通知。

可视化：提供最新数据、图形、聚合图形、拓扑图、仪表盘与自定义报表。

分布式监控：通过 Zabbix Proxy 实现对多机房、跨网络区域的分布式数据采集与代理告警。

自动化发现：支持网络发现、自动注册、低级别发现（LLD），自动纳管主机与监控项。

开放接口：提供完整的 REST API，便于与 CMDB、自动化平台、告警中心集成。


### 1.3 监控模型

Zabbix 的监控数据模型可归纳为一条自上而下的主线：

主机 (Host)  ─▶  监控项 (Item)  ─▶  触发器 (Trigger)  ─▶  动作 (Action)

│                 │                    │                    │

被监控对象        采集的指标          阈值判断逻辑         告警通知与自动处理

│

└─▶  模板 (Template)  ─▶  监控项/触发器/图表/应用集 的复用集合

即：先定义监控哪些主机，为主机绑定模板自动生成监控项，再由触发器对监控项的值进行判定，条件满足时通过动作执行通知或远程命令。

### 2.2 数据流向

从数据产生到最终展示与告警，Zabbix 的数据流大致经过以下几个环节：

① 采集：Server 的 Poller 主动拉取，或 Agent/Sender 主动推送到 Trapper。

② 预处理：对原始值进行单位换算、正则提取、JSONPath 解析、去重等预处理。

③ 存储：数值写入数据库的 history 表，同时更新 trends 趋势表用于长期统计。

④ 判定：触发器对最新值求值，状态发生变化时生成 Problem 或 Recovery 事件。

⑤ 动作：动作（Action）根据条件触发通知、执行远程命令或升级处理。

⑥ 展示：Web 前端从数据库读取数据，渲染图形、仪表盘与告警列表。


### 2.3 通信端口与协议


| 组件 | 默认端口 | 说明 |
|---|---|---|
| Zabbix Server | 10051 | 接收 Agent/Proxy 的主动上报与 Proxy 数据 |
| Zabbix Agent | 10050 | 被动模式下接受 Server 的采集请求 |
| Zabbix Proxy | 10051 | 代替 Server 采集并向 Server 上报 |
| Zabbix Web | 80 / 443 | HTTP/HTTPS 管理界面与 API |
| Java Gateway | 10052 | JMX 监控网关（可选组件） |
| 数据库 | 3306 / 5432 | MySQL/MariaDB 或 PostgreSQL |


## 3. 核心组件详解


### 3.1 Zabbix Server（服务端）

Zabbix Server 是整个监控系统的 核心大脑，负责采集调度、数据处理、触发器计算、告警生成与配置管理。它由一组按职能划分的内部进程（Process）组成，通过多进程并发实现高吞吐。

主要内部进程及其职责：


| 进程类型 | 职责 |
|---|---|
| Poller（轮询器） | 主动向 Agent/SNMP/IPMI 等发起采集请求，拉取监控数据 |
| Trapper（接收器） | 被动接收 Agent 主动推送、Sender 数据以及 Proxy 上报 |
| Preprocessor / History Syncer | 数据预处理、写入历史与趋势数据 |
| Pinger / Discovery / Autoregistration | ICMP 探测、网络发现与主机自动注册 |
| Escalator（升级器） | 按升级策略处理长时间未恢复的告警 |
| Alerter（告警器） | 执行动作，发送邮件、短信、Webhook 等通知 |
| Timer / Housekeeper | 定时任务与历史数据清理（回收过期数据） |
| Configuration Syncer | 从数据库缓存配置，供其他进程读取 |

关键点：Server 不直接保存数据到磁盘的文本文件，而是将所有配置、历史与趋势数据写入关系型数据库；同时 Server 是无状态的，多个实例配合数据库可实现高可用。


### 3.2 Zabbix Agent（客户端）

Zabbix Agent 部署在被监控主机上，负责执行具体的指标采集。它是轻量级的 C 语言程序，资源占用低。Zabbix 提供两代 Agent：

Zabbix Agent（经典版）：以 C 语言编写，体积小、稳定性高，通过内置键值（如 system.cpu.load、vfs.fs.size）采集系统指标。

Zabbix Agent 2（新一代）：基于 Go 语言编写，支持插件化扩展、可加载自定义插件，内置更多开箱即用的采集能力，适合云原生与现代环境。

按照数据获取方向，Agent 有两种工作模式：


| 模式 | 数据流向 | 特点 |
|---|---|---|
| 被动模式（Passive） | Server 轮询 Agent（10050）拉取数据 | 配置简单，但大规模下 Server 压力较大 |
| 主动模式（Active） | Agent 主动推送到 Server（10051） | 降低 Server 压力，适合大规模与跨网段场景 |

Agent 配置示例（zabbix_agentd.conf）：

Server=192.168.1.100          # 被动模式：允许哪些 Server 采集本机

ServerActive=192.168.1.100     # 主动模式：向哪个 Server 上报

Hostname=web01                # 主机名，需与 Web 端配置一致

UserParameter=custom.db.conn,mysql -e "show status" | grep Threads | awk '{print $2}'


### 3.3 Zabbix Proxy（代理）

Zabbix Proxy 用于 分布式监控，部署在远程区域或网络隔离环境中，代替 Server 完成本地数据采集，再把数据统一上报给 Server。它自带一个独立的本地数据库（SQLite 或 MySQL/PostgreSQL），可独立缓存数据并在网络恢复后续传。

主要价值：分担 Server 负载、减少跨广域网的流量、适应防火墙隔离区域、在网络中断时缓存数据避免丢失。


| Proxy 模式 | 说明 |
|---|---|
| 主动模式 | Proxy 主动连接 Server 上报数据，只需 Proxy 能访问 Server，适合网络单向可达场景 |
| 被动模式 | Server 主动连接 Proxy 拉取数据，需要 Server 能访问 Proxy 端口 |


### 3.4 数据库

数据库是 Zabbix 的 数据持久化核心，存储所有配置信息（主机、模板、触发器）、历史数据（history）与趋势数据（trends）。Zabbix 支持多种关系型数据库：


| 数据库 | 特点 | 适用场景 |
|---|---|---|
| MySQL / MariaDB | 最常用、生态成熟、社区资料多 | 中小规模与通用场景 |
| PostgreSQL | 功能强大、并发性能好 | 中大型规模、对数据完整性要求高 |
| TimescaleDB | 基于 PostgreSQL 的时序扩展，自动分区与压缩 | 大规模、海量历史数据场景 |

容量规划要点：Zabbix 数据量取决于监控项数量与采集频率。需重点关注 history 表的增长速度，合理配置保留周期（Housekeeping），或启用分区/压缩以控制数据库体积。


### 3.5 Web 前端

Zabbix Web 前端基于 PHP 开发，通常运行在 Nginx 或 Apache 之上，是运维人员与系统交互的主要入口。它从数据库读取配置与数据，提供图形化操作界面。

核心功能模块：

Monitoring：查看仪表盘、问题列表、最新数据、图形、拓扑图与告警概览。

Inventory：管理主机资产信息。

Configuration：配置主机、模板、监控项、触发器、动作与自动发现规则。

Administration：管理用户、权限、认证、媒介类型与系统设置。

Reports：生成可用性报告、触发器 TOP 排名、审计日志等。

此外，Web 前端还暴露 /api_jsonrpc.php 接口，支持通过 REST API 以编程方式管理监控对象与查询数据。


### 3.6 扩展组件


| 组件 | 作用 |
|---|---|
| Zabbix Sender | 由脚本或程序调用，主动向 Server 推送自定义数据（zabbix_sender） |
| Zabbix Get | 命令行工具，用于测试 Server 到 Agent 的采集是否正常（zabbix_get） |
| Java Gateway | 通过 JMX 协议监控 Java 应用（Tomcat、Kafka 等） |
| SNMP / IPMI | 监控网络设备、交换机、带外管理卡与硬件传感器 |
| Webhook / 媒介脚本 | 对接企业微信、钉钉、Slack、PagerDuty 等告警渠道 |


## 4. 工作流程说明


### 4.1 数据采集流程

以被动采集为例，一次完整的指标采集经过如下步骤：

① 定时触发    Server 的 Poller 根据 Item 的采集间隔（如 60s）发起任务

② 建立连接    Poller 通过 TCP 10050 连接目标主机的 Zabbix Agent

③ 发送请求    请求某个 Key，例如 system.cpu.util[,idle]

④ Agent 采集  Agent 调用对应的采集逻辑，读取 CPU 空闲率

⑤ 返回结果    以 ZBXD 协议返回数值，如 87.3

⑥ 预处理      单位换算、正则/JSONPath 提取、去重与丢弃无效值

⑦ 入库        写入 history 表，并按小时粒度更新趋势 trends 表

⑧ 触发器求值  计算触发器表达式，状态变化时生成 Problem / Recovery 事件

⑨ 动作执行    匹配 Action 条件，发送告警或执行远程命令


### 4.2 告警处理流程

Zabbix 的告警由 触发器（Trigger） 与 动作（Action） 共同完成。触发器负责“判定异常”，动作负责“如何处理”。

# 触发器表达式示例：CPU 空闲率连续 5 分钟低于 20% 则告警

{web01:system.cpu.util[,idle].avg(5m)} < 20

# 触发器可设置在恢复时自动关闭，也可配合依赖关系抑制级联告警

动作（Action）的典型处理链：

条件匹配：按主机组、触发器严重级别、时间段等条件筛选事件。

执行操作：发送通知、执行远程命令、调用 Webhook 集成工单系统。

告警升级：若问题在设定时间内未恢复，逐级通知上级负责人（Escalation）。

自动恢复：触发器恢复正常后，发送恢复通知并关闭问题。


### 4.3 分布式采集流程

引入 Proxy 后，数据流变为两级结构：

Agent/设备 ──▶ Zabbix Proxy ──(缓存)──▶ Zabbix Server ──▶ 数据库

(本地采集与告警)         (集中存储与展示)

特点：网络中断时 Proxy 本地缓存数据，恢复后自动续传，避免数据丢失。


## 5. 典型应用场景


### 5.1 主机监控

对服务器的基础资源进行统一监控，包括 CPU、内存、磁盘、网络、进程、端口与系统负载等，通过模板实现批量配置。

操作系统指标：CPU 利用率、内存使用、磁盘空间与 IO、网卡流量、系统负载、文件句柄数。

服务可用性：关键进程是否存在、端口是否监听、URL 是否可访问。

批量纳管：通过自动注册或网络发现，新上线主机自动套用模板，实现零人工配置。


### 5.2 指标采集

Zabbix 支持多种采集方式，可覆盖从物理设备到应用层的全栈指标：


| 采集方式 | 协议/机制 | 适用对象 |
|---|---|---|
| Zabbix Agent | ZBXD 协议（10050/10051） | Linux/Windows 主机 |
| SNMP | v1/v2c/v3 轮询与 Trap | 交换机、路由器、打印机等网络设备 |
| IPMI | 带外管理接口 | 服务器硬件、风扇、温度、电源 |
| JMX | Java Gateway（10052） | Tomcat、Kafka 等 Java 应用 |
| HTTP Agent | HTTP/HTTPS 请求 | REST API、Web 服务健康检查 |
| 脚本与 Sender | 自定义脚本 + zabbix_sender | 业务指标、批处理结果 |
| 数据库监控 | ODBC/自定义 Key | MySQL、PostgreSQL 等数据库 |

低级别发现（LLD）：可自动发现主机上的磁盘、网卡、文件系统、容器等动态对象，并自动为其创建监控项与触发器，非常适合磁盘/分区频繁变动的环境。


### 5.3 触发器告警

通过触发器表达式对采集值进行实时判定，实现阈值告警、趋势告警与组合条件告警。

# 磁盘使用率超过 90%

{web01:vfs.fs.size[/,pused].last()} > 90

# 5 分钟内服务端口不可达

{web01:net.tcp.service[tcp,,80].max(5m)} = 0

# 连续 3 次采集都异常（避免抖动误报）

{web01:agent.ping.nodata(90s)} = 1

# 多条件组合：CPU 高 且 负载高

({web01:system.cpu.util[,idle].avg(5m)} < 20) and

({web01:system.cpu.load[percpu,avg1].avg(5m)} > 2)

告警收敛：可通过触发器依赖（Dependency）抑制因网络故障引发的级联告警，通过 nodata() 函数检测数据中断，避免“监控失联”被忽略。


### 5.4 可视化展示

Zabbix 提供丰富的可视化手段，帮助运维人员快速掌握系统状态：

最新数据与图形：单个监控项的历史曲线，支持自定义时间段对比。

聚合图形：把多个监控项的图形拼合到同一页面，适合整体概览。

仪表盘（Dashboard）：拖拽式构建自定义面板，组合问题列表、图形、拓扑、SVG 组件等，支持按用户与角色共享。

拓扑图（Map）：以图形化方式呈现主机与网络链路关系，可动态表示主机可用状态与链路流量。

报表：可用性报告、触发器 TOP 榜、审计日志，支撑容量分析与合规审计。


### 5.5 分布式监控

对于多数据中心、多云或网络隔离的大型环境，使用 Proxy 构建分布式监控体系：

区域代理：在每个机房部署 Proxy，本地采集只回传汇总数据，减少骨干网带宽占用。

网络隔离：在 DMZ 或生产隔离区部署 Proxy，Server 无需直接访问受控网段。

故障容错：Proxy 本地缓存，网络恢复后自动续传，避免数据缺口。

水平扩展：通过 Proxy 分摊采集压力，使单套 Zabbix 支撑更大规模主机。


## 6. 常见部署模式对比


### 6.1 部署模式一览


| 部署模式 | 架构组成 | 优点 | 缺点 | 适用规模 |
|---|---|---|---|---|
| 单机模式 | Server + DB + Web + Agent 同机 | 部署简单、资源占用低、易维护 | 单点故障、扩展性差 | 小型环境 / 测试 |
| Server-Agent 集中式 | Server + DB + Web 独立，Agent 分布 | 结构清晰、集中管理、性能可控 | 跨网段采集消耗带宽、Server 压力集中 | 中小型生产环境 |
| 分布式 Proxy | Server + 多 Proxy + DB + Web | 分担负载、支持跨区域、容错性好 | 架构复杂、需额外维护 Proxy 与本地库 | 大型 / 多机房环境 |
| 高可用（HA） | 多 Server 节点 + 共享 DB + 负载均衡 Web | 消除单点、提升可用性 | 数据库仍是瓶颈、运维成本高 | 关键业务 / 大规模 |
| 容器化部署 | Docker / K8s 编排各组件 | 弹性伸缩、快速交付、便于升级 | 需熟悉容器运维、存储需外置 | 云原生 / 弹性环境 |


### 6.2 模式选择建议

规模较小或首次试用：选择单机模式，快速验证功能。

单一数据中心、主机数量中等：采用 Server-Agent 集中式，将数据库独立部署以保证性能。

多机房 / 跨区域 / 主机量大：引入 Proxy 分区采集，每个区域一个 Proxy，降低带宽与 Server 负载。

对可用性要求高：采用 Server HA 架构，并将数据库做主从或集群，Web 前端做负载均衡。

云原生或弹性伸缩环境：选择容器化部署，配合自动注册与 LLD 动态纳管实例。


### 6.3 关键设计考量


| 考量维度 | 要点 |
|---|---|
| 数据库性能 | 选用高性能磁盘（SSD），合理设置历史数据保留周期，必要时使用分区或 TimescaleDB |
| 采集规模 | 根据监控项数量估算 NVPS（每秒新值数），据此规划 Server 与数据库配置 |
| 网络带宽 | 跨区域采集优先使用主动模式或 Proxy，减少不必要的往返 |
| 高可用 | Server 支持 HA 集群；数据库需做主从/集群；Web 层可水平扩展 |
| 安全 | 启用 TLS 加密 Agent-Proxy-Server 通信，API 使用 Token 或严格权限控制 |
| 容量规划 | 预留 30% 以上资源余量，定期评估 history/trends 增长趋势 |


## 7. 最佳实践与小结


### 7.1 最佳实践

模板化管理：统一通过模板下发监控项与触发器，避免逐台手工配置，保证一致性。

主动模式优先：大规模环境下优先使用主动模式或 Proxy，显著降低 Server 压力。

合理设置采集间隔：核心指标 30–60s，次要指标可放宽，避免产生海量无效数据。

历史数据分层：短期保存精细历史，长期仅保留趋势（trends），控制数据库体积。

告警分级与收敛：设置合理的严重级别与依赖关系，减少告警风暴与误报。

监控数据中断告警：使用 nodata() 检测采集失联，确保“沉默”也可见。

定期演练与审计：验证告警通路有效性，定期审查模板与权限配置。

自动化集成：通过 API 与自动注册接入 CMDB 和自动化平台，实现主机上线即可监控。


### 7.2 小结

Zabbix 以 Zabbix Server 为核心，Zabbix Agent 负责主机侧采集，Proxy 实现分布式扩展，数据库提供持久化存储，Web 前端承载管理与可视化，各组件分工明确、协同工作。

围绕“主机 → 监控项 → 触发器 → 动作”的数据主线，Zabbix 完成了从数据采集、阈值判定、告警通知到可视化展示的完整闭环。它既适用于单机小规模场景的快速部署，也能通过 Proxy 与高可用架构支撑跨机房、大规模的企业级监控需求，是 Linux 运维体系中应用最为广泛的监控平台之一。
