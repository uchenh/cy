### 2. Ceph 的基本术语（同事听不懂你就输了）

在讲 P3 之前就先把这几个词定义清楚：

| 术语 | 一句话解释 | 类比 |
|---|---|---|
| **RADOS** | Ceph 的底层存储引擎（Reliable Autonomic Distributed Object Store） | 地基 |
| **Object（对象）** | Ceph 存的最小单位，默认 4MB | 一块积木 |
| **PG（Placement Group）** | 对象的逻辑分组，用来减少管理开销 | 一筐积木 |
| **Pool（存储池）** | PG 的集合，一个池可以独立设置副本策略 | 一个仓库 |
| **CRUSH** | 算出数据该存在哪个 OSD 的算法 | 地图导航（不用查表） |
| **OSD** | 真正读写磁盘的进程 | 仓库管理员 |
| **MON** | 维护集群地图的进程 | 调度中心 |

### 3. 你必须能回答的 3 个核心问题

| 问题 | 答案要点 | 对应页 |
|---|---|---|
| Ceph 和传统 SAN/NAS 比，优势在哪？ | 去中心化、线性扩展、通用硬件、故障自愈（P3–4） | P3–4 |
| Ceph 的数据可靠性怎么保证？ | 三副本/纠删码 + CRUSH 分布到不同故障域 + Scrub 巡检（P16–17） | P16–17 |
| 客户端读写数据，中间经过了多少层？ | 写 6 步，读 1 步；关键点：MON 不在数据路径上（P14–15） | P14–15 |

### 4. 常见坑 / 生产注意事项（加分项）

讲到 P8（OSD）或 P16（副本 vs 纠删码）时，主动提一句生产经验：

- **MON 一定要 3 个或 5 个**（奇数个），不能偶数——偶数个 MON 并不会提高容忍度，反而浪费资源（P6）。
- **OSD 的容量建议整盘使用**，不要分区再给 Ceph，BlueStore 直接管理裸盘效率最高（P8）。
- **纠删码不适合热数据**，因为编码/解码开销大，RBD 和 CephFS 元数据池一定要用三副本（P16）。
- **CRUSH Map 的故障域设计很重要**——小集群用 host 级就行，别过度设计（P13）。

#### P7 MGR（Manager）

- **区分 MON vs MGR**（这是最容易混淆的）：
  - MON 管一致性（集群状态的唯一权威）
  - MGR 管可观测（图表、告警、指标）
- **类比**：MON 是交警（管交通规则），MGR 是监控摄像头（记录违章数据）。

#### P8 OSD（Object Storage Daemon）— 最重要的一页

- **一定要强调**：「OSD 是唯一真正读写磁盘的组件，整个集群跑多少个 OSD，取决于你有多少块数据盘。」
- 分 5 个小块讲，每块 30 秒：
  1. 数据存储（BlueStore 直接管理裸盘）
  2. 数据读写（客户端直连 OSD，不经过中间层）
  3. 副本复制（主 OSD 同步给副本 OSD）
  4. 故障检测与恢复（心跳机制）
  5. 自动再平衡（扩缩容无感）
- **生产经验加分**：BlueStore 是 Ceph 当前的默认存储后端，性能远超之前的 FileStore。

#### P9 MDS（Metadata Server）

- **一句话**：MDS 只为 CephFS 服务，RBD 和 RGW 都不经过它。
- **类比**：MDS 是文件系统的「前台接待」，目录查询它来，但数据存取直接去仓库（OSD）。

#### P10 RGW（RADOS Gateway）

- **关键点**：RGW 是无状态的，前面挂 Nginx/HAProxy 做负载均衡就行。
- **类比**：RGW 就像 AWS S3 的「替身」，API 完全兼容，但数据存在你自己的集群里。

### 第三部分：基本原理（P11–17）— 约 10 分钟

这部分偏原理，建议配合白板或手绘辅助讲解。

#### P11 对象、PG、Pool 三层抽象

- **用收纳盒类比**：
  - Object = 一本书
  - PG = 一个书架（把多本书放一起管理）
  - Pool = 一个书架区（可以设不同规则，比如小说区、教材区）
- **关键数字**：对象默认切成 4MB。

#### P12 CRUSH 算法（重点！）

- **一句话定义**：CRUSH = Controlled Replication Under Scalable Hashing
- **核心思想**：数据在哪，不靠查表，靠算。
- **四个特性**（每特性 30 秒）：
  1. 伪随机但确定（同输入同输出）
  2. 均匀分布
  3. 故障域感知（副本在不同主机/机架）
  4. 增量迁移（加一块盘只搬 1/N 的数据）
- **类比**：就像每个人按同一份规则把书放到不同的书架上，不用问图书管理员。

#### P13 CRUSH Map — 故障域设计

- 简单带过，重点讲「故障域」概念。
- **生产建议**：小集群用 host 级就够了。

#### P14 写入路径（六步）

- **建议手绘流程图**（或指向 PPT 上的图），一步一步讲。
- 关键节奏：客户端 → MON 拿地图 → 算 CRUSH → 写主 OSD → 主 OSD 同步副本 OSD → 全部确认返回。
- **强调**：写操作要走 6 步，所以延迟比读高。

#### P15 读取路径

- **一句话总结**：读比写快，因为只需要 1 步网络 IO（直接找主 OSD 拿数据）。
- 补充：随机小块读可以用 SSD 缓存池加速。

#### P16 副本 vs 纠删码

- **这是选型的关键决策点**，建议重点讲。
- 用对比表讲（PPT 已做了对比图）：
  | | 三副本 | 纠删码（4+2） |
  |---|---|---|
  | 空间开销 | 3 倍 | 1.5 倍 |
  | 读取性能 | 从任一副本读 | 需要解码 |
  | 适合场景 | 热数据、RBD、CephFS | 冷数据、对象存储 |
- **记住一句话**：热数据用副本，冷数据用 EC。

#### P17 副本与自愈

- 简单带过，和 P16 一起讲就行。
- **加分点**：提一下 Scrub（数据巡检）——后台定期做校验和比对，发现静默坏块自动修复。

### 第四部分：三种接口深入（P18–21）— 约 8 分钟

这部分最贴近实际使用，建议让感兴趣的同事重点关注。

#### P18 RBD 块存储

- **一句话**：RBD 就是给虚拟机或容器当硬盘用的。
- **关键场景**：KVM/OpenStack 虚拟机磁盘、K8s 持久卷。
- **亮点特性**：COW 克隆（节省空间）、Mirror（灾备复制）。

#### P19 CephFS 文件系统

- **一句话**：CephFS 就是让多台机器像 NFS 一样挂载同一个目录，但是分布式的。
- **关键场景**：HPC 共享目录、K8s ReadWriteMany PVC。
- **亮点特性**：多 Active MDS 按目录分片，元数据性能线性扩展。

#### P20 RGW 对象存储

- **一句话**：RGW 给你一个自建的 S3，API 和 AWS S3 完全一样。
- **关键场景**：图片视频存储、备份归档、数据湖。
- **亮点特性**：多租户认证、生命周期策略、版本控制、多站点同步。

#### P21 三种接口怎么选（重点页！）

- **这张表是整份 PPT 最有价值的决策工具**，建议逐行讲。
- **最后那句口诀一定要让大家记住**：
  > 虚拟机/数据库 → RBD；共享目录 → CephFS；海量存储 → RGW。
