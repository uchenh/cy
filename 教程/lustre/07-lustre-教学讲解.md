## 1. Lustre 是什么?一句话结论

Lustre 是一个开源的高性能**并行分布式文件系统**(Parallel Distributed File System):它把一份文件拆成多块、同时写入多台服务器的多个磁盘,让成千上万个计算节点像访问本地目录一样并发读写同一份共享数据,**聚合带宽随存储节点数量线性增长**。专为 HPC 超算、AI 训练这类"多机并发读大文件"场景设计,名字取自 **Linux + Cluster**。

它要解决的问题:普通文件服务器(NFS)撑不住几千个节点同时读一个大文件——单台机器的磁盘带宽就是上限。Lustre 的思路是"让 N 台机器一起干活,带宽乘以 N"。

## 2. 整体架构:元数据与数据彻底分离

Lustre 性能的核心来自**分离式架构**——"文件叫什么、在哪"(元数据)与"文件内容存哪"(数据)是两条完全独立的链路。

```
                          +-----------------------------+
                          |          Clients            |
                          |  (lustre.ko 内核模块)       |
                          +--------------+--------------+
                                         |  LNet (TCP / InfiniBand / RoCE)
                  +----------------------+----------------------+
                  |                      |                      |
           +------v------+       +-------v-------+      +-------v-------+
           |     MGS     |       |      MDS       |      |      OSS       |
           |  (MGT 配置) |       |  (MDT 元数据)  |      |  (OST 数据对象) |
           +-------------+       +-------+-------+      +-------+-------+
                                       |                       |
                               元数据/布局信息            条带化对象数据
```

**图书馆类比**:

- **MGS(M**anagement **S**erver)+ **MGT** = 图书馆总台:保存"书架在哪、谁负责"的登记簿(config log,配置日志)。客户端挂载时先来找总台拿地图。
- **MDS(M**etadata **S**erver)+ **MDT** = 目录卡片管理员:管文件名叫什么、放哪个书架、权限归谁,但不碰文件内容。
- **OSS(O**bject **S**torage **S**erver)+ **OST** = 书架:真正存放数据,每个 OST 后端是本地文件系统(ldiskfs 或 ZFS)。
- **Client** = 读者:装内核模块 `lustre.ko` 后挂载为本地目录,用标准 `cp`/`ls`/`cat` 访问。
- **LNet(L**ustre **Net**working)**:网络抽象层,承载所有节点间通信,支持 TCP/InfiniBand(`o2ib`)/RoCE。

**关键机制:数据 IO 直连**。客户端读写文件内容**不经过 MDS**,而是按 MDS 给出的布局信息直连 OSS。元数据走窄路、数据走宽路,互不堵塞——这是高吞吐的第一个来源。

## 3. 关键机制

### 3.1 条带化(Striping)

把一个文件拆成多块同时写多个磁盘:16 MiB 数据拆成 4 段写 4 块盘,吞吐接近单盘 × 4。

| 参数 | 含义 | 典型取值 |
|------|------|----------|
| `stripe_count` | 文件用几个 OST(条带宽度) | 默认 1;大文件 `-1` 用满所有 OST |
| `stripe_size` | 每个条带单元大小 | 默认 1 MiB;大顺序 IO 调 4~8 MiB |
| `stripe_offset` | 起始 OST 索引 | `-1` 由 MDS 自动轮转 |

配置命令:

```bash
lfs setstripe -c 4 -S 4M -i -1 /mnt/lustre/bigfile.dat   # 文件级
lfs setstripe -c -1 -S 1M /mnt/lustre/dataset            # 目录默认布局,新文件继承
```

进阶:**PFL(渐进式布局)**——文件前 1 MiB 用 1 个 OST,超过阈值自动扩到多 OST,兼顾小文件开销与大文件带宽;创建时小、后期变大的文件用固定条带不经济。

### 3.2 LDLM 锁机制

**LDLM(L**ustre **D**istributed **L**ock **M**anager,分布式锁管理器)保证多客户端数据一致。类比多人协作编辑文档:客户端只对文件某个**字节区间**持锁(Extent 锁),改不同段落可并行;改同一段要等对方"写完保存"——持有者收到**回调(callback)**后刷回脏数据并释放锁。

锁模式从松到严:`NL`(占位)→ `PR`(保护读)→ `PW`(保护写)→ `EX`(独占)。Lustre 默认 POSIX 一致性(close-to-open)。代价是**锁争用**:大量小文件并发写同一目录是性能瓶颈,部署时要分散热点目录。

### 3.3 故障恢复(Failover / Recovery)

- **active/passive 双机共享存储**:MDS/OSS 故障由备用节点挂载同一后端盘秒级接管(生产用 Pacemaker + Corosync 编排)。
- **客户端重放**:服务端故障期间客户端 IO 阻塞、持续重连;服务恢复后**重放(replay)**未完成操作日志,事务不丢。
- 超过恢复窗口会被驱逐(evicted),重新挂载即可。
- MGT 必须高可用(它是集群挂载的前提);脑裂靠共享存储 fencing 避免双写。

## 4. 典型应用场景与适用边界

**适合**(多机并发读大文件、需要高聚合带宽):HPC 超算、AI 训练大数据集并发读、影视渲染、科学仿真、PB 级科研数据共享。

**边界**:

- 部署运维复杂:内核模块、LNet、版本与内核强绑定
- 小文件/元数据密集场景不占优(锁争用 + MDT 瓶颈,需 DNE 缓解)
- 无原生纠删码,冗余靠 FLR 镜像,容量开销大
- 不适合跨地域(低延迟局域网设计)
- 加 OST 在线扩容容易,移除 OST 必须先迁移数据

## 5. 与 Ceph 的差异(一句话概括)

Lustre 是为"极致聚合带宽"而生的并行文件系统;Ceph 是"对象/块/文件三合一"的统一存储平台。同规模下 Lustre 高带宽与条带控制更精细,但 Ceph 部署简单、自愈强、生态通用。**HPC 大文件并发选 Lustre,云原生通用存储选 Ceph**。详细对比见 `docs/03-lustre-vs-ceph-对比.md`。

## 6. 核心组件速查表

| 组件 | 全称 | 角色 | 图书馆类比 |
|------|------|------|-----------|
| **MGS** | Management Server | 集群"大脑",存配置日志,挂载入口 | 图书馆总台 |
| **MGT** | Management Target | MGS 的存储目标(几 GB 够,必须高可用) | 总台登记簿 |
| **MDS** | Metadata Server | 管目录树、inode、权限、文件布局 | 目录卡片管理员 |
| **MDT** | Metadata Target | MDS 的存储目标(建议 SSD) | 卡片柜 |
| **OSS** | Object Storage Server | 提供数据服务,每台管 1~N 个 OST | 书架管理员 |
| **OST** | Object Storage Target | 存数据对象,后端 ldiskfs/ZFS | 书架 |
| **Client** | 客户端 | 内核模块 `lustre.ko`,挂载为本地目录 | 读者 |
| **LNet** | Lustre Networking | 网络抽象层(TCP/InfiniBand/RoCE) | 馆内通道 |
