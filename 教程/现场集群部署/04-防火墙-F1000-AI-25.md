# 04 · 边界防火墙 F1000-AI-25

> **设备角色**：唯一公网出入口 —— 出口路由 + NAT（出/入双向）+ 安全策略 + SSL VPN 网关。
> **不承担**内网三层网关（那是 S6880 的职责），只与 S6880 有一条 `/30` 互联。
> **配套**：《配置命令执行手册.md》阶段 0 / 4 / 7 / 8；《HPC集群网络配置方案.md》§5。

## 2. 接口配置（阶段 4.1）

```
system-view

# —— 外网线（每运营商只启用一条）——
interface GigabitEthernet1/0/1
 port link-mode route
 ip address 60.191.84.165 255.255.255.248
 description CT-LINE 60.191.84.160/29 gw .161
 undo shutdown
interface GigabitEthernet1/0/2
 port link-mode route
 ip address 101.71.15.156 255.255.255.248
 description CU-LINE 101.71.15.152/29 gw .153
 undo shutdown

# —— 第二条线：插着，但不配 IP（物理备用）——
interface GigabitEthernet1/0/0
 description CT-SPARE-NO-IP
interface GigabitEthernet1/0/3
 description CU-SPARE-NO-IP

# —— 内网口（10GE SFP+，接 S6880）——
interface Ten-GigabitEthernet1/0/26
 port link-mode route
 ip address 192.168.254.1 255.255.255.252
 description TO-S6880
 undo shutdown
quit
```

| 接口 | IP | 掩码 | 角色 |
|---|---|---|---|
| `GE1/0/1` | 60.191.84.165 | /29 | 电信主线（在用） |
| `GE1/0/2` | 101.71.15.156 | /29 | 联通主线（在用） |
| `GE1/0/0` | 无 | — | 电信第二条线（备用，不配 IP） |
| `GE1/0/3` | 无 | — | 联通第二条线（备用，不配 IP） |
| `XGE1/0/26` | 192.168.254.1 | /30 | 内网口 → S6880 `1/0/47`（.2） |

> **为什么第二条线不配 IP**：同运营商的四条线是**同 /29 同网段**交付（电信两条都属 `60.191.84.160/29`、联通两条都属 `101.71.15.152/29`），而 **H3C 不允许同一台设备两个三层接口落在同一网段** ⇒ 第二个口配 IP 必报
> `This subnet overlaps with another interface!`（与 S6880 的 `Vlan-if10` / M-GE 冲突同源）。
> ⇒ 本期**每个运营商只启用一条线**，主备退化为**运营商级**（电信 → 联通）。两条不同运营商的线本身已互为备份。
> 补建方案见本篇 §6。

> ⚠ **`port link-mode route`**：部分 F1000 型号出厂时**只有 `GE1/0/1` 是三层口**，其余电口是二层口（已加入 VLAN 1），其上 `ip address` 命令根本不存在，会有一批 WAN 口配不上地址、主备设计整体失效。
> **本台实测**（2026-09-23）：`GE1/0/0`–`1/0/25` 出厂即为三层口 ⇒ 该命令对它是**幂等保险**，照敲无害。换同系列其他机型时务必保留这一步。

security-zone name Trust

quit
security-zone name Untrust
 import interface GigabitEthernet1/0/0

quit

| 安全域 | 成员接口 | 含义 |
|---|---|---|
| `Trust` | `XGE1/0/26`（内网口） | 内网（管理网 + 业务网经 S6880 的流量都从这里进） |

| `VPN` | `SSLVPN-AC 1`（隧道接口） | SSL VPN 客户端 |

## 4. 路由：双出口主备（浮动路由 + NQA + Track）

**设计**：两条缺省路由分别绑定出接口与运营商网关，`track` 联动 NQA 探测结果，`preference` 决定优先（电信 60 < 联通 70）。线路故障 → Track 转 Negative → 该路由失效 → 自动切到另一条；恢复后按 preference 回切。

### 4.1 NQA 探测（阶段 4.3）

```
nqa entry admin ctline
 type icmp-echo
  destination ip 60.191.84.161
  source ip 60.191.84.165
  frequency 100
  probe timeout 500
  reaction 1 checked-element probe-fail threshold-type consecutive 3 action-type trigger-only
 quit
quit

nqa entry admin culine
 type icmp-echo
  destination ip 101.71.15.153
  source ip 101.71.15.156
  frequency 100
  probe timeout 500
  reaction 1 checked-element probe-fail threshold-type consecutive 3 action-type trigger-only
 quit
quit

# ⚠ 系统视图下一起启动（不能写在 nqa entry 内部，也不能在用户视图 <H3C> 下敲）
nqa schedule admin ctline start-time now lifetime forever
nqa schedule admin culine start-time now lifetime forever
```

| 参数 | 值 | 说明 |
|---|---|---|
| 探测方式 | `icmp-echo` | 对运营商网关做 ICMP 探测 |
| 探测目标 | 电信 `60.191.84.161` / 联通 `101.71.15.153` | **取本线路的运营商网关** —— 在直连网段内，路由表已有直连路由，探测自动从对应接口发出，**无需 `out interface` / `next-hop`**，少两个出错点 |
| 源地址 | 本线接口地址 | 明确从哪条线发出 |
| 频率 | 100 ms | |
| 超时 | 500 ms | |
| 判定 | **连续 3 次失败** 触发 | |
| 联动 | `action-type trigger-only` | ⚠ **必须显式写**，缺省 `none` 只显示结果不通知 Track |

> ⚠ **四个已踩过的坑**：
> 1. **`admin-name` 与 `operation-tag` 不能含连字符 `-`** —— `nqa entry admin ct-main` 报 `Invalid operation tag`，改用 `ctline` / `culine`。名字没建成功会导致后续 `type`/`destination` 连环报 Unrecognized。
> 2. **`nqa schedule` 属系统视图** —— 既不能写在 `nqa entry` 里，也不能在用户视图 `<H3C>` 下敲（2026-09-23 现场两种错法都踩到）。
> 3. **`reaction` 必须写 `action-type trigger-only`** —— 缺省 `action-type none` ⇒ Track 永久 `NotReady`、浮动路由完全不生效（**现场卡最久的一条**）。症状：`display nqa result` 有数据，但 `display track N` 一直 `NotReady`。⚠ 联动项建好后**不能改**，只能 `undo nqa entry` 删掉整条重配。
> 4. **`next-hop` 必须带 `ip` 关键字** —— 写 `next-hop ip <地址>`；写 `next-hop <地址>` 报 Unrecognized。

### 4.2 Track 联动（阶段 4.4）

```
track 1 nqa entry admin ctline reaction 1
quit
track 2 nqa entry admin culine reaction 1
quit
```

> ⚠ **`track` 命令会进入 track 子视图**（提示符变 `[H3C-track-1]`），紧跟的 `ip route-static` 会打在子视图里报 Unrecognized。**每条 `track` 后加一句 `quit`。**
> ⚠ 别手动数 `quit` 层数（NQA 有"操作视图 → 测试类型视图"两层、不同固件落点不一致，多退一层就到用户视图）：**每小段开头一律敲 `system-view` 兜底**（已在系统视图时无副作用），看到尖括号 `<H3C>` 就是退过头了。

**兜底方案（固件不支持 NQA 时）**：改用接口联动（只能探到物理链路 down，探不到"链路在但 ISP 侧不通"，但零配置、够稳）：

```
undo track 1
quit
undo track 2
quit
track 1 interface GigabitEthernet1/0/1
quit
track 2 interface GigabitEthernet1/0/2
quit
```
（track 编号不变，下面的浮动路由不用改）

### 4.3 浮动默认路由与回程明细路由（阶段 4.5）

```
ip route-static 0.0.0.0 0 GigabitEthernet1/0/1 60.191.84.161 track 1 preference 60
ip route-static 0.0.0.0 0 GigabitEthernet1/0/2 101.71.15.153 track 2 preference 70
ip route-static 192.168.0.0 16 192.168.254.2
```

| 路由 | 下一跳 | Track | Preference | 作用 |
|---|---|---|---|---|
| 缺省 | `GE1/0/1` 60.191.84.161 | track 1 | **60** | 电信优先 |
| 缺省 | `GE1/0/2` 101.71.15.153 | track 2 | **70** | 联通备份 |
| `192.168.0.0/16` | 192.168.254.2 | — | 60（缺省） | **回程明细路由**：覆盖 `192.168.10.0/24`、`192.168.11.0/24`、`192.168.99.0/24` 等全部内网，保证入站流量从原线路返回 |

> ⚠ **关键字顺序**：`track` 必须**紧跟下一跳**、写在 `preference` **之前**。
> ✅ 正确：`ip route-static 0.0.0.0 0 GigabitEthernet1/0/1 60.191.84.161 track 1 preference 60`
> ❌ 错误：`... preference 60 track 1` → 报 `% Too many parameters found at '^' position.`

**切换行为**：电信线故障 → 秒级切联通（pref 70）；恢复后按 60 < 70 自动回切。**同运营商内部的两线冗余本期不具备**（见 §6）。

## 5. NAT

### 5.1 出方向 NAT（Easy-IP，阶段 4.6）

```
acl advanced 3000
 rule permit ip source 192.168.10.0 0.0.0.255
 rule permit ip source 192.168.11.0 0.0.0.255
quit

interface GigabitEthernet1/0/1
 nat outbound 3000
interface GigabitEthernet1/0/2
 nat outbound 3000
```

| 项 | 值 |
|---|---|
| 方式 | **Easy-IP**（源地址转换成出接口地址） |
| 匹配源 | `192.168.10.0/24`（BMC/管理）+ `192.168.11.0/24`（业务） |
| 应用接口 | 两个**在用** WAN 口（`.165` / `.156`） |
| 效果 | 内网任意主机、任意端口可出网；会话表 `display nat session` 可见转换条目 |

### 5.2 入方向 NAT Server（阶段 7）

**⚠ 前置：发布 IP 必须先落到接口上**，否则设备不应答其 ARP、外部流量根本到不了。
`60.191.84.166` / `101.71.15.158` **不在任何接口上** ⇒ 作为**同接口的次要地址（sub）**加上去：

```
interface GigabitEthernet1/0/1
 ip address 60.191.84.166 255.255.255.248 sub
quit
interface GigabitEthernet1/0/2
 ip address 101.71.15.158 255.255.255.248 sub
quit
```

> ⚠ 同接口加 `sub` 地址**不受**"两个三层接口不能同网段"限制（那条限制说的是两个**不同**接口）。

```
nat server protocol tcp global 60.191.84.166 443  inside 192.168.11.11 443
nat server protocol tcp global 60.191.84.166 6022 inside 192.168.11.11 22
nat server protocol tcp global 101.71.15.158 443  inside 192.168.11.11 443
nat server protocol tcp global 101.71.15.158 6022 inside 192.168.11.11 22
# 固件支持命名时（便于 display nat server 辨识）：
# nat server protocol tcp global 60.191.84.166 443 inside 192.168.11.11 443 rule ct-platform
```

| 公网地址 | 公网端口 | 内网目标 | 内网端口 | 用途 |
|---|---|---|---|---|
| 60.191.84.166 | 443 | 192.168.11.11 | 443 | 电信线发布平台 HTTPS |
| 60.191.84.166 | 6022 | 192.168.11.11 | 22 | 电信线发布平台 SSH（**外部 6022 → 内部 22**） |
| 101.71.15.158 | 443 | 192.168.11.11 | 443 | 联通线同上 |
| 101.71.15.158 | 6022 | 192.168.11.11 | 22 | 联通线同上 |

> ⚠ **`nat server` 后面没有"规则名"参数位**。官方语法为
> `nat server [ protocol pro-type ] global { global-address | ... } [ global-port ] inside local-address [ local-port ] [ rule rule-name ]`
> —— 名字（若固件支持）只能放在**行尾 `rule <name>`**；不支持的固件直接省略，不影响映射功能。

> 入站回程说明：H3C NAT Server 的会话会**自动从接收请求的接口原路返回**，无需额外策略路由。外部用户跨运营商访问（如联通用户访问电信地址）时响应仍从电信线返回，属正常。
> 公网 DNS 需为同一域名在电信/联通**各解析一条 A 记录**（智能 DNS），入站才能按线路分流。

## 6. 同运营商双线如何才能真正启用（本期未用）

现场实测证明"独立双口 + 各自配 IP"在 H3C 上走不通。要启用同运营商的两条线只有三条路：

| 方案 | 做法 | 评价 |
|---|---|---|
| ① 运营商改网段 | 让两条线各拿独立 `/29`，则四层浮动路由（60/65/70/75）完全可用 | **语义最清晰、排障最方便**；需走运营商工单，有交付周期 |
| ② **Reth 冗余接口** | 三层逻辑接口，两个物理口做成员、主备切换，**只有一个 IP**，天然规避同网段限制；备成员口不转发，**不会形成环路**（优于聚合）<br>`interface Reth1` → `member interface GigabitEthernet1/0/0 priority 255` → `member interface GigabitEthernet1/0/1 priority 100` → `ip address 60.191.84.164 255.255.255.248` | 需现场用 `interface Reth1` 试（F1000 各代支持情况不同） |
| ③ 三层聚合口（Route-Aggregation） | 也可绕过限制，但两个成员口**同时转发**，若运营商两条线落在**同一个二层域**会形成环路/广播风暴 | ⚠ **采纳前必须先向运营商确认两条线上行形态**，风险高于 Reth |

## 7. 安全策略（阶段 4.7 / 7.2 / 8）

> **本方案共 11 条基础规则 + 2 条可选规则**。默认策略为拒绝，所以"该放的都要显式放"。

### 7.1 基础放行（阶段 4.7）

```
security-policy ip
 rule name LAN-to-WAN
  source-zone Trust
  destination-zone Untrust
  source-ip-subnet 192.168.0.0 255.255.0.0
  action pass
 quit
 rule name Local-to-LAN
  source-zone Local
  destination-zone Trust
  action pass
 quit
 rule name Local-to-WAN
  source-zone Local
  destination-zone Untrust
  action pass
 quit
 rule name LAN-to-Local
  source-zone Trust
  destination-zone Local
  action pass
 quit
quit
```

| 规则 | 方向 | 用途 |
|---|---|---|
| `LAN-to-WAN` | Trust → Untrust | 内网出公网 |
| `Local-to-LAN` | Local → Trust | **设备自己** ping 内网 / 探测内网侧 |
| `Local-to-WAN` | Local → Untrust | **设备自己** ping 公网 / **NQA 探测** |
| `LAN-to-Local` | Trust → Local | 内网 ping / 访问设备 |

> ⚠ **设备自身发出的报文属 `Local` 安全域，默认不放行 —— 三个方向缺一不可。**
> 2026-09-23 现场实测：漏了 **`Local→Untrust`** 会导致设备 ping 公网、**NQA 探测全部失败**，极易误判成线路或模块故障。

### 7.2 入站发布（阶段 7.2）

```
 rule name WAN-to-Platform-443
  source-zone Untrust
  destination-zone Trust
  destination-ip-host 192.168.11.11
  service-port tcp destination eq 443
  action pass
 rule name WAN-to-Platform-6022
  source-zone Untrust
  destination-zone Trust
  destination-ip-host 192.168.11.11
  service-port tcp destination eq 6022
  action pass
 quit
```

> ⚠ **安全策略的 `service` 只接受「一个服务对象组名 | any」，不能写 `tcp-443` 这类裸端口名**；
> 按端口放行要用 **`service-port tcp destination eq <端口>`**，且**一条命令只能带一个目的端口** ⇒ 443 与 6022 必须拆成两条规则。

### 7.3 SSL VPN 相关（阶段 8，详见 [07 篇](./07-客户远程接入-SSLVPN.md)）

```
 rule name VPN-Login
  source-zone Untrust
  destination-zone Local
  destination-ip-host 60.191.84.165
  service-port tcp destination eq 4430
  action pass
 quit
 rule name VPN-to-MGMT-443          # BMC 网页
  source-zone VPN
  destination-zone Trust
  source-ip-subnet 192.168.99.0 255.255.255.0
  destination-ip-subnet 192.168.10.0 255.255.255.0
  service-port tcp destination eq 443
  action pass
 quit
 rule name VPN-to-MGMT-22           # 管理设备与服务器带外 SSH
  source-zone VPN
  destination-zone Trust
  source-ip-subnet 192.168.99.0 255.255.255.0
  destination-ip-subnet 192.168.10.0 255.255.255.0
  service-port tcp destination eq 22
  action pass
 quit
 rule name VPN-to-MGMT-IPMI
  source-zone VPN
  destination-zone Trust
  source-ip-subnet 192.168.99.0 255.255.255.0
  destination-ip-subnet 192.168.10.0 255.255.255.0
  service-port udp destination eq 623
  action pass
 quit
 rule name VPN-to-BIZ              # 业务网全端口（客户"用机"端口无法穷举）
  source-zone VPN
  destination-zone Trust
  source-ip-subnet 192.168.99.0 255.255.255.0
  destination-ip-subnet 192.168.11.0 255.255.255.0
  action pass
 quit
```

| 规则 | 用途 | 端口 |
|---|---|---|
| `VPN-Login` | 客户端拨入 SSL VPN 网关 | TCP 4430 |
| `VPN-to-MGMT-443` | 开服务器 BMC 网页 | TCP 443 |
| `VPN-to-MGMT-22` | SSH 到 S6880 / S5120V3 / MQM8790 / 带外 | TCP 22 |
| `VPN-to-MGMT-IPMI` | IPMI over LAN | UDP 623 |
| `VPN-to-BIZ` | SSH / 传数据到业务网节点 | **全端口** |

> ⚠ **两道过滤，顺序不能反**：`filter ip-tunnel acl 3999`（SSL VPN 网关层，按**目的 IP**）→ 安全策略（按安全域 + 服务）。
> 客户端**只能**访问 ACL 里 permit 的目的地址，其余一律被网关丢弃（末尾隐含 deny）—— **安全策略放行了也没用**。2026-09-24 现场在这里卡得最久。

### 7.4 两条可选规则（按需启用）

```
# ① 远程运维防火墙自身（人在外地也要改防火墙时）
 security-policy ip
  rule name VPN-to-Local-SSH
   source-zone VPN
   destination-zone Local
   service-port tcp destination eq 22
   action pass
  quit
 quit
 save force

# ② 物理链路未通时，先验证"客户端 → 防火墙 → S6880"整条转发链
 rule name VPN-to-SW
  source-zone VPN
  destination-zone Trust
  source-ip-subnet 192.168.99.0 255.255.255.0
  destination-ip-subnet 192.168.254.0 255.255.255.252
  action pass
```

> ⚠ **连接 VPN 后各目标的统一管理入口（2026-09-24 实测）**：

| 目标 | 从 VPN 用哪个地址 | 靠哪条策略放行 |
|---|---|---|
| **防火墙** | **`192.168.99.254`**（隧道网关 = 设备自身，同 VPN 域） | 无需额外策略；仅需 ACL 3999 放行 `192.168.99.0/24` |
| S6880 | `192.168.10.254`（`Vlan-if10`，Trust 域） | `VPN-to-MGMT-22` |
| S5120V3 | `192.168.10.251` | `VPN-to-MGMT-22` |
| MQM8790 | `192.168.10.252` | `VPN-to-MGMT-22` |
| 服务器 OS | `192.168.11.11`–`.20` | `VPN-to-BIZ` |
| 服务器 BMC | `https://192.168.10.11`–`.20`（**必须带 `https://`**） | `VPN-to-MGMT-443` |

> ⚠ 防火墙**不能**用管理口地址 `192.168.10.253` —— 管理口属 `Management` 域，不在放行范围；改用隧道网关 `.99.254`。
> ⚠ 连通性验证用 **`Test-NetConnection <地址> -Port 22`** 或直接 SSH，**不要用 ping**（上述策略均未放行 ICMP）。
> ⚠ **加 `VPN-to-Local-SSH` 之前必须先把客户账号口令与设备 admin 口令分离** —— 该策略对所有 VPN 用户生效。

## 11. 本篇相关坑（详见 [11-附录B](./11-附录B-现场坑与排障.md)）

1. 同运营商的第二条线配 IP 报 `This subnet overlaps with another interface!`
2. `port link-mode route` 漏配（换机型时）→ 一批 WAN 口配不上地址
3. NQA 名字含连字符 → `Invalid operation tag`，且会连环报 Unrecognized
4. 联动项缺 `action-type trigger-only` → Track 永久 NotReady
5. `nqa schedule` 写在错误视图 → Unrecognized
6. `track` 进入子视图未 `quit` → 紧跟的路由报 Unrecognized
7. `ip route-static` 中 `track` 与 `preference` 顺序写反 → `Too many parameters`
8. 缺 `Local→Untrust` → 设备 ping 公网、NQA 全失败
9. 安全策略 `service` 写裸端口名 → 不生效，要用 `service-port`
10. `nat server` 前置名字位不存在 → 名字放行尾 `rule <name>`
11. 发布 IP 未落到接口 → 设备不应答 ARP，外部访问不通
12. 21 号口是千兆区，插 10G 内网链路起不来
13. `XGE1/0/26` / `MGE1/0/0` 只是显示缩写，配置要用全名
