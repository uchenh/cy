1. 概述

1.1 背景

客户已采购朴赛 GPU 计算集群（含管理节点、存储节点、计算节点及 InfiniBand/以太网网络设备）。计划于下周一（2026 年 8 月 3 日）在 IDC 机房完成服务器及 IB 网络设备上架组网后，面向大模型分布式训练场景开展系统性性能验证，确认硬件配置正确、单机与集群算力达标、IB 网络带宽/时延/稳定性满足训练通信要求，并验证多节点分布式训练任务可正常运行。

1.2 适用范围

本规划适用于本次交付集群的现场验收测试、问题排查及性能测试报告编制，覆盖硬件检查、单机性能、IB 网络、NCCL 通信及分布式训练端到端验证。

1.3 参考依据

• 设备报价配置清单（集群朴赛整机类报价模板）

• NVIDIA A800 / CUDA / NCCL 官方文档与性能建议

• Mellanox/NVIDIA InfiniBand 部署与 OFED 驱动手册

• 客户机房机柜、电力、散热及网络接入条件确认单（现场补充）

2. 测试目标

本次测试旨在全面验证交付集群是否满足大模型分布式训练业务需求，具体目标如下：

G1 硬件配置正确性：核对服务器/GPU/内存/存储/网卡/电源等与合同及报价配置一致，固件与驱动版本合规，无硬件告警。

G2 单机计算性能：验证单节点 CPU、GPU（A800×8）、内存带宽及本地存储 I/O 达到预期基线，GPU 间互联（NVLink）工作正常。

G3 集群计算性能：验证 4 节点集群在多卡、多机并行计算场景下的聚合算力与扩展效率。

G4 IB 网络性能：验证 200Gbps InfiniBand 链路带宽、端到端时延、丢包/重传及长时间稳定性。

G5 分布式训练正常性：验证基于 NCCL 的多节点通信与典型大模型训练任务可稳定跑通，吞吐量与收敛行为符合预期。

3.2 InfiniBand 网络拓扑

采用单台 MQM8700（200G IB）作为高性能计算/训练通信平面核心交换机，管理节点、存储节点及 4 台计算节点均通过 200G IB 网卡接入，形成星型（星形汇聚）拓扑。业务管理与带外/带内管理平面走千兆以太网交换机。推荐逻辑划分如下：

• 计算平面（IB）：4×计算节点 + 管理节点 + 存储节点 ↔ MQM8700（200G InfiniBand）

• 管理平面（Eth）：各节点 BMC/管理口及业务管理网 ↔ 千兆以太网交换机

• 存储访问：训练数据优先经 IB 或高速路径访问存储节点（具体挂载方式现场确认：NFS/并行文件系统等）

• 机柜部署：42U 机柜×2，计算节点（4U×4）与管理/存储/交换设备合理分柜，兼顾散热、承重与线缆长度

[计算节点1..4] ──200G IB──┐
[管理节点]     ──200G IB──┼── MQM8700 (IB 200G 40口)
[存储节点]     ──200G IB──┘
各节点 BMC/管理口 ── 千兆以太网交换机 ── 机房管理网

5. 具体测试项目与步骤

测试按模块顺序执行：上架通电检查 → 硬件核对 → 单机性能 → IB 网络 → 集群 NCCL → 分布式训练 → 稳定性与收尾。每步保留原始输出日志，文件命名建议：日期_主机名_用例名.log。

5.1 模块 A：上架组网与基础连通性

目的：确认物理部署、供电、网络连通与设备可管理。

A1. 按机柜平面图完成设备上架固定，核对电源线接入 PDU 相位与冗余。

A2. 连接 IB 线缆至 MQM8700，连接管理网至以太网交换机；统一线缆标签。

A3. 上电：交换机 → 管理/存储 → 计算节点；观察风扇、指示灯、BMC 可访问。

A4. 配置管理网 IP，SSH 登录各节点；同步时钟（NTP/chrony）。

A5. 加载 IB 驱动，检查 ibstat / ibdev2netdev，确认端口 Active、速率 200Gb/s。

A6. 管理网 ping 全通；IB 平面可达（IPoIB 或 RDMA 设备可见）。

5.2 模块 B：硬件配置正确性核查

B1. CPU：核对型号、核数、插槽数（计算节点应为 EPYC 9554×2）。

B2. 内存：核对容量与条数（计算节点 64GB×16）；检查 CE/UE 告警。

B3. GPU：nvidia-smi -L / -q，确认 A800 80GB×8，PCIe 代际与链路宽度正常。

B4. 存储：系统盘/数据盘容量、RAID/NVMe 状态；SMART 健康。

B5. 网卡：IB HCA 型号与固件；以太网口速率。

B6. 电源与散热：冗余电源在位；传感器温度在阈值内。

B7. 输出《硬件配置核对表》，与报价单逐项签字确认。

5.3 模块 C：单机计算与 GPU 性能

C1. 在单台计算节点执行 CUDA bandwidthTest，记录 Host↔Device、Device↔Device 带宽。

C2. 执行 p2pBandwidthLatencyTest，确认 GPU 间 P2P/NVLink 可达与带宽。

C3. 单机 8 卡 nccl-tests all_reduce_perf（如 -b 8 -e 2G -f 2 -g 8），记录 busbw。

C4. （可选）fio 对本地 SSD/存储节点挂载路径做顺序读写基线。

C5. 四台计算节点分别执行并对比，偏差过大则排查 NUMA 绑定、PCIe、散热降频。

5.4 模块 D：IB 网络带宽 / 时延 / 稳定性

D1. 链路层：ibstat、iblinkinfo；必要时 ibdiagnet 导出拓扑与错误计数。

D2. 点对点带宽：节点间两两（或抽样全互联）运行 ib_write_bw / ib_read_bw，记录峰值与均值。

D3. 时延：ib_write_lat / ib_send_lat，记录典型消息大小下的时延。

D4. 稳定性：选定 1～2 对节点持续跑带宽测试 ≥ 2 小时（或约定时长），观察错误计数、重传、端口 Down。

D5. 交换机侧：检查端口错误、拥塞相关计数；确认无异常端口抖动。

5.5 模块 E：多节点 NCCL 通信

E1. 确认 NCCL 使用 IB（NCCL_IB_DISABLE=0 等环境变量按基线配置）。

E2. 2 节点×8 卡 all_reduce_perf，记录算法带宽/总线带宽。

E3. 4 节点×8 卡（共 32 GPU）all_reduce_perf，覆盖多种 message size。

E4. 对比单机 / 2 机 / 4 机扩展效率，识别通信瓶颈。

E5. （可选）补充 all_gather、reduce_scatter 等集合操作抽测。

5.6 模块 F：分布式训练端到端验证

F1. 准备统一容器/conda 环境与模型代码；数据落存储节点或本地缓存策略确认。

F2. 单机 8 卡试跑，确认 loss 下降、无 OOM、GPU 利用率合理。

F3. 多机启动（torchrun / deepspeed / 调度系统提交）：2 节点 → 4 节点递进。

F4. 记录训练吞吐量（tokens/s 或 samples/s）、step time、通信占比、MFU（如可算）。

F5. 故障注入抽测（可选）：杀一进程后任务退出/重启策略是否符合预期。

F6. 与客户确认业务侧验收用例（若有指定模型与数据集，以其为准）。

5.7 模块 G：稳定性与收尾

G1. 按约定执行 ≥ 4～8 小时（或客户要求更长）训练/NCCL soak。

G2. 检查 dmesg、BMC、交换机日志：GPU Xid、IB 链路、ECC、温度告警。

G3. 整理原始日志、截图、核对表；填写测试记录与问题单。

G4. 输出性能测试报告初稿，组织客户现场确认。

7. 风险项与排错方案


| 风险 | 可能表现 | 排查与应对措施 |
|---|---|---|
| 电力/散热不足 | 掉电、降频、GPU 温度高、时钟下降 | 核对 PDU 容量与冗余；改善风道；降低并行度临时验证；协调机房扩容 |
| IB 线缆/端口故障 | 端口 Down、带宽低、时延高、NCCL 超时 | ibstat 查 State/Rate；更换线缆与对端端口；更新 HCA/交换机固件；清洗连接器 |

| NCCL 拓扑异常 | 多机带宽差、扩展比差 | NCCL_DEBUG=INFO 分析；检查 NCCL_IB_HCA、NUMA 亲和；确认无禁用 IB |
| GPU 故障/Xid | 训练中断、掉卡、ECC 暴涨 | 记录 Xid；nvidia-smi -q；单卡隔离复现；申请换卡 |
| 存储瓶颈 | 训练 step 时间长、GPU 利用率低、数据等待 | fio 定位；增加本地缓存/预取；优化 DataLoader；检查挂载协议 |
| 配置与报价不符 | 部件型号/数量不一致 | 对照装箱单与序列号；开具差异单；补货后重测相关项 |
| 时间窗口紧张 | 无法完成 soak 与全量用例 | 优先执行 B/D/E/F 关键路径；稳定性改为夜间 soak；出具阶段性报告 |
| 权限与变更 | 无法安装驱动/改配置 | 提前申请 root/变更窗口；准备离线安装包与回退方案 |

7.1 现场排错基本原则

• 先物理后逻辑：指示灯/线缆/端口 → 驱动 → 配置 → 应用。

• 先单机后集群：单卡 → 单机 8 卡 → 2 机 → 4 机。

• 保留证据：命令、日志、时间戳、变更记录同步归档。

• 变更可控：固件/驱动变更需记录版本，避免多人同时改环境。
