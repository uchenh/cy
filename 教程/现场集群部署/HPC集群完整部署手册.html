三、这套系统的形态（一句话）

边界防火墙 + 1 台三层业务交换机 + 1 台二层管理交换机 + 1 台独立 IB 算力交换机 + 10 台服务器（1 管理/登录 + 8 GPU + 1 存储）， 管理网 192.168.10.0/24（VLAN 10）与业务网 192.168.11.0/24（VLAN 11）共用一台 S6880 做三层网关， 出口为电信 + 联通双线主备，客户经 SSL VPN 从公网接入管理网与业务网， 计算通信走完全独立的 200G InfiniBand fabric（10.20.0.0/16）。

01 · 总览与拓扑

本篇回答：这套集群长什么样、每台设备干什么、线怎么连、地址怎么分。 逐设备的配置命令见 02–07；按顺序施工见 08；判据见 09。

1. 系统定位与设计目标

一套部署在单一机房内的 HPC 算力集群，面向 GPU 训练/推理与并行计算负载，同时需要对外开放（对外发布 Web 服务）与对外授权使用（异地客户远程使用机器）。

设计上要同时满足五件事：

# 目标 落地手段
1 管理与业务流量隔离 双 VLAN：VLAN 10 = 带外管理（BMC），VLAN 11 = 业务（含存储前端）
2 出口不中断 双运营商（电信 + 联通）浮动路由主备，NQA 探测 + Track 联动自动切换
3 内网出口与入站可控 NAT outbound（Easy-IP）出方向 + NAT Server 精确端口发布入方向
4 异地客户可"管理 + 使用" SSL VPN IP 接入，下发管理网 + 业务网两个网段路由
5 计算通信高性能 独立 200G InfiniBand fabric，与以太网完全物理隔离

8. 设计原则（七条）

  1. 三层网关收敛在业务交换机 —— S6880 单机作为全网唯一三层网关（Vlan-if10 / Vlan-if11），防火墙只做出口路由 + NAT + 策略。单机形态没有设备级冗余，因此每个阶段结束都 save force。
  2. 管理网不直连防火墙 —— BMC/带外网段经 trunk → S6880 → 防火墙访问外网，中间必须过网关，便于统一控制。
  3. 算力网物理隔离 —— IB fabric 独立组建，无以太网网关、无跨网路径；PKey（Partition）用于逻辑隔离计算与存储流量（当前单平面未实施，见 06 篇）。
  4. 双运营商主备出口 —— 浮动静态路由 + Track/NQA 探测 + 出接口 Easy-IP NAT。因同网段限制，本期退化为运营商级主备（电信 60 → 联通 70），同运营商内部两线冗余未启用。
  5. 每个 VLAN 一段统一配置、不绑定具体节点 —— 交换机下联口只按 access VLAN 划分，节点换插口只需换线，交换机零改动。
  6. 管理与计算分离 —— Slurm 管理面与 NFS 走 25G 业务网（不依赖 IB 的 SM）；IB 只留给 MPI/NCCL 计算通信。这样任一侧升级都不影响另一侧。
  7. 命令与文档同源 —— 所有命令语法均按 H3C Comware 7 / NVIDIA Onyx 官方参考核对过，现场踩到的差异（视图层级、参数顺序、端口名）全部回写进文档。

8. 安全建议（四条）

# 建议 做法
1 限源 客户在深圳的出口 IP 固定时，给 VPN-Login 加 source-ip-subnet <客户出口IP> 255.255.255.0，把 4430 从"对全网开放"收成"只对客户出口开放"
2 按端口收紧业务网 VPN-to-BIZ 目前是全端口放行（客户"用机"端口无法穷举）。若只需 SSH，改成 service-port tcp destination eq 22；若只需其中几台机器，把 ACL 3999 的第 2 条改成具体节点地址（如 192.168.11.13 0.0.0.0）—— ACL 改动即时生效、客户端无需重连
3 留审计 每客户独立账号（本方案已如此）；在线会话 display sslvpn session；停用某人直接 state block / undo local-user
4 加设备自身运维通道时先分离口令 需要"人在外地也能改防火墙"时补 VPN-to-Local-SSH（只放 22、不放 443）。⚠ 加之前必须先把客户账号口令与设备 admin 口令分离 —— 该策略对所有 VPN 用户生效

业务网全端口放行是安全上最需要关注的一条：等于把算力集群对客户侧开放。上面第 2 条是最直接的收紧手段。

11. 本篇相关坑（详见 11-附录B）

  1. 两层过滤顺序搞反 —— ACL 3999 比安全策略更靠前，不放行目的 IP 就出不去（卡最久的一条）。
  2. sslvpn enable 报 Unrecognized —— 本机固件没有这条命令，SSL VPN 默认可用，跳过即可。
  3. display sslvpn user 不存在；display local-user user-name X 后面必须跟 class。
  4. filter ip-tunnel acl 漏配 = 不做访问控制。
  5. service-type sslvpn 漏配 = 用户登不上。
  6. iNode 网关栏不带端口 = 连不上（默认打到 443）。
  7. iNode 安装包必须用登录页那份 —— 别处下载的可能识别不了网关。
  8. 只放行特定 TCP 端口的策略不能用 ping 验证 —— ICMP 没被放行，ping 必然超时，不能据此判断策略无效。
  9. 新版 OpenSSH 的 ssh-rsa 报错 —— 换客户端或加 -o HostKeyAlgorithms=+ssh-rsa。
  10. 客户端本地网段冲突 —— 客户电脑所在网络也用 192.168.10.x / 192.168.11.x 时，VPN 路由会被本地路由抢走（表现为"能连上但 ping 不通"）。
  11. 入口单点 —— 网关只挂电信 .165，电信线故障时 VPN 入口随之中断（集群仍能出网）。要入口备份，在联通侧再建一个 sslvpn gateway（101.71.15.156 port 4430）绑同一 context（多网关支持以实测为准）。
  12. BMC 页面必须带 https:// —— 且从 VPN 访问时只放行 443、未放行 80。

4. 兼容性注意事项

4.1 H3C 光模块厂商校验

H3C 交换机默认校验光模块厂商信息，非原装/认证模块可能被识别为不合规并关端口 —— 优先买 H3C 原厂或明确兼容型号。

本项目实况（2026-09-23 实测）：现场模块均为第三方（SHENGWEI 25G、Mellanox 25G、FINISAR 10G）。在 S6880 上插第三方模块会打一条 A non-H3C transceiver is detected 的告警日志，但端口仍正常识别与工作 —— 只是提醒，不是端口被关。 判据：看 display logbuffer，只有"速率/类型与配置不匹配"才是真问题。

⚠ 防火墙（F1000-AI-25）侧对第三方模块的校验策略未实测；若 1/0/26 插 FINISAR 后不 up，先看 display logbuffer 有无关端口告警。

4.2 NVIDIA 线缆认证

HDR 200G DAC/AOC 选 NVIDIA 官方认证型号（MFS/MCP 系列），非认证线在 HDR 速率下易出现误码。

4.3 SFP28 对 1G 的支持（本方案的关键不确定点 → 已消除）

SFP28 口对 1G 的支持随批次有差异。本方案 S6880 ↔ S5120V3 这条上行链路只能走 1G，涉及两个未验证项： ① 该 SFP28 口能否降到 1G；② 是否兼容 1000BASE-T 电口模块（电口模块对设备的要求通常比光模块更严格）。

✅ 2026-09-24 实测：两项都成立 —— 模块插入 1/0/48 后 25GE1/0/48 UP、速率 1G，模块被正常识别，Vlan10 随之 up ⇒ 管理网打通。

退化路径（本次未用到，保留）： - 退路① 换成 1G 光模块（1000BASE-LX/SX），两端光口对接； - 退路② 把管理交换机换成 S5120V3-52S-SI（带 1G/10G SFP+），两端用 10G 模块跑 10G，最稳但需采购周期。 ⚠ 模块占用冲突：现场两只能用的 10G 模块（FINISAR）已分配给 FW ↔ S6880 的 1/0/47；走退路②需另购 2 只 10G 模块，不能挪用 FW 链路那两只。

8. 四套排障流程

8.1 ssh 到设备超时

1. 网线是否直插这台设备的管理口（不是业务口、不是别的交换机）
   ⚠ 笔记本不插网线必然 timeout
2. 笔记本 IP：直连 M-GE 用 192.168.9.100/24（网关留空）；接管理网用 192.168.10.x
   ipconfig 确认；同时连着 Wi-Fi 就先禁用 Wi-Fi
3. 先 ping 后 ssh：ping 192.168.9.250（或 192.168.10.254）
   通了但 ssh 超时 → Console 查 display ssh server status
   不通 → 回到第 1、2 步
4. 设备侧口状态：display interface M-GigabitEthernet0/0/0 看 Line protocol state: UP

判据速记：Permission denied = 已连上（密码错）；Connection refused = SSH 服务没开；timeout = 包没到。

8.2 服务器"网卡 up 但上不了网"

1. S6880 上 display interface brief → 找出 UP 的那个口
2. display vlan → 看这个口属于哪个 VLAN
   ⚠ 只有 1/0/1–1/0/12 是 access VLAN 11；1/0/13–1/0/46 属 VLAN 1（没有网关）
3. 不在 VLAN 11 → 换口，或把该口划进来：
   interface <该接口全名>
    port link-type access
    port access vlan 11
4. 再 ping 192.168.11.254 → 通则网关 OK；ping 223.5.5.5 → 通则出口 NAT OK
   （不通再查防火墙 ACL 3000 与 nat outbound）

8.3 VPN 连上但访问不了内网

1. 先看第一道过滤：acl advanced 3999 是否 permit 了目标网段（⚠ 比安全策略更靠前）
2. 再看安全策略：display security-policy ip（VPN→Trust 的对应端口规则）
3. 再看回程：S6880 与 S5120V3 是否各有 ip route-static 192.168.99.0 24
4. 最后看物理链路：Vlan-if10 / Vlan-if11 是否 up（这是最常见根因）
5. 客户端侧：route print 是否有两条内网路由；本地网段是否冲突

8.4 IB 起不来 / 带宽异常

1. ibstat -l → 确认本机 IB 卡设备号（mgmt01=mlx5_0；gpu/stg=mlx5_2）
2. mlxconfig -d /dev/mst/mt4123_pciconf0 q → LINK_TYPE_P1 是否为 1（IB）
3. ibstat → State 是否 Active、Rate 是否 200
4. 线缆是否 NVIDIA 认证 HDR 型号
5. sminfo → 是否有且仅有一个 SM（无双 SM 抢权）
6. ib_write_bw --report_gbits <对端> → ≥ 190 为正常（实测 196.83）

8.5 作业提交后 PENDING

squeue -j <JobID> -o "%.18i %.9P %.8j %.2u %.2t %.10M %.6D %R"
REASON 含义 处理
Priority 有更高优先级作业在前面 等待，或 sprio -j <JobID> 看差距
Resources 资源暂时不够 等，或降低 -c / --mem / --gres
ReqNodeNotAvail 指定节点不可用 去掉 -w 或换节点

最常见原因：GPU 要多了（--gres=gpu:8 却只想用一张）、内存要超了（--mem=1000G 但单节点上限 1000G）。
